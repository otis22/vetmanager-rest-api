# Локальный запуск и проверки

## Цель

Воспроизводимо собрать проект локально, включая PHP 7.3, и проверить библиотеку на тестовом домене devtr6 перед ревью PR #26.

## Исходные факты

- 20.10.2026 `make build PHP_VERSION=7.3` завершился с exit 2: Alpine 3.15 не содержит `icu-data-full`.
- `make all PHP_VERSION=8.3` ранее проходил; интеграция без локальных тестовых данных не выполнялась.
- CI по двум событиям запускает Coveralls и интеграцию. На предыдущих запусках PR #26 Coveralls вернул 422, а API — 401; остальные задания отменились.
- Тестовые `TEST_DOMAIN` и `TEST_API_KEY` доступны локально в `vetmanager-mcp/.env`; значения не включаются в git, PR, CI или лог.

## Работа и приёмка

1. Исправить сборку PHP 7.3 без изменения публичного API и проверить `make all PHP_VERSION=7.3` и `make all PHP_VERSION=8.3` реальными запусками с exit codes.
2. Локально сопоставить `TEST_DOMAIN` из `vetmanager-mcp/.env` с `TEST_DOMAIN_NAME`, который читает эта библиотека; перед запросами проверить, что итоговый домен — именно devtr6. Выполнить интеграционные тесты, различая дефекты кода и состояние данных стенда. `AuthTest::testServiceApiKey` проверять отдельно: его нельзя объявить пройденным без service-учётных данных.
3. Обновить безопасный образец конфигурации и инструкции, если фактический запуск этого требует.
4. Разобрать статусы всех jobs матрицы CI, конфликт двойного запуска `push`/`pull_request` и причины Coveralls 422 / интеграции 401; устранить подтверждённые препятствия в пределах этой задачи, не копируя локальный ключ в CI.
5. Получить независимое ревью этого PRD до реализации и diff после неё, разобрать замечания, записать точные команды, коды завершения и ограничения.

## Границы

Не менять публичный API, production, CI secrets, статус merge. Секреты использовать только локально и никогда не выводить в артефакты.

## Ревью и проверки

20.10.2026 отдельный агент `/root/prd_review` провёл read-only ревью PRD до реализации. Приняты замечания о сопоставлении переменных, проверке `make all` на 7.3, отдельном service-тесте, зависимости от данных devtr6 и критерии по CI; раздел приёмки уточнён.

Отдельный агент `/root/diff_review` провёл read-only ревью diff после реализации. Его замечание medium о снятии автоматического интеграционного гейта закрыто явным правилом локальной проверки в `AGENTS.md` и ограничением в этом PRD. Замечание low о сохранении полного ICU для PHP 7.4 закрыто сужением условия Dockerfile до версии 7.3. Повторное ревью итогового diff: замечаний нет; `git diff --check` — exit 0.

### Решения

- В Alpine 3.15 для PHP 7.3 не устанавливается отсутствующий `icu-data-full`; для PHP 7.4 и 8.x остаётся прежняя установка полного набора ICU.
- Отсутствие service-учётных данных даёт явный пропуск одного теста. API-key интеграция выполняется на devtr6.
- В обычной CI-матрице выполняются Composer validate, стиль, статический анализ, unit и покрытие. Coveralls запускается один раз на push в `main` под PHP 8.3; интеграция с отдельными CI-секретами запускается вручную через `workflow_dispatch`. Это исключает 401 от устаревших CI-секретов из PR-гейта, не выдавая интеграцию за зелёную.
- Изменение гейта отражено в `AGENTS.md`: для PR с изменением исполняемого кода или тестов требуется локальный результат `make integration` на devtr6. Автоматическое покрытие интеграцией всей PHP-матрицы до настройки отдельных CI-секретов отсутствует и остаётся ограничением ревью.

Локальный `.env` содержит только `TEST_DOMAIN_NAME=devtr6` и тестовый `TEST_API_KEY`; файл игнорируется Git. В `vetmanager-mcp/.env` не было `SERVICE_NAME` / `SERVICE_API_KEY`. Предыдущие CI-запуски PR #26 имели 401 на интеграции, Coveralls 422 и отменённые jobs; новая CI-конфигурация ещё должна подтвердиться запуском GitHub Actions после push. Живую интеграцию в CI до обновления отдельных CI-секретов считать непроверенной.
