# O5: узкий JSON PUT Unit — 2026-10-26

## Контракт и граница

На devtr6 проверен `PUT /rest/api/Unit/50` с JSON `{"title": "<технический маркер>"}`: HTTP 201, JSON `success=true`; GET по тому же ID подтвердил техническую запись. Поэтому допустимо добавить к опциональному `Methods\Unit` метод `put(Headers $headers, int $id, array $body): ResponseInterface`, который только передаёт вызывающему Guzzle клиенту `PUT`, `uri('Unit', $id)->asString()`, исходные headers и `json => $body`. Ответ и исключения остаются исходными. Вызывающий код отвечает за допустимость ID, состав тела и жизненный цикл записи. Семантика частичного PUT и сохранность неуказанных полей не доказаны; метод не обещает их. Сигнатура `uri(string $model, ?int $id = null)` и класс `WithId` подтверждены в исходниках.

Отрицательные wire-пробы на этой записи: `title:null` → 406; неизвестное поле → 406. PUT с техническим маркером `o5u47a0b7a8256dx` вернул 201, а GET подтвердил сохранение ровно 16 символов. Прежнее описание маркера как 17-символьного ошибочно; wire-поведение для 17 символов не проверено. В исходнике ExtJS `rest/protected/models/Unit.php` для `title` заданы `required` и `max=16`; в закреплённом OpenAPI указано `x-db-type: varchar(16)`, но JSON-Schema `maxLength` отсутствует. Эти источники не доказывают поведение devtr6 для 17 символов. Поэтому валидатор, DTO, ограничения длины и изменение upstream OpenAPI не входят в этот PR. `schema_support` остаётся `none`.

Порядок: до POST Redash дал ноль по точному маркеру в 08:57:23Z; GET списка также дал ноль; POST 201 вернул ID 50 и этот ID сразу записан в `/tmp/o5-unit-probe.NQTFHc/created-id` на хосте; GET 200 подтвердил ID и маркер. Затем PUT с маркером → 201, PUT `title:null` → 406, PUT с 16-символьным маркером → 201, PUT с неизвестным полем → 406. После PUT маркер стал `o5u47a0b7a8256dx`; первый автоматический cleanup остановился на несовпадении с первоначальным маркером. Redash в 08:58:26Z подтвердил единственную запись ID 50 с новым техническим title. Повторный GET сверил точные ID 50 и новый title; лишь затем DELETE 200/success=true. GET по ID вернул пустую коллекцию, GET списка не нашёл префикс маркера, Redash DS 6 в 08:59:15Z дал ноль по ID и префиксу маркера. Доказательство принадлежности записи: предварительный ноль, уникальный маркер, сохранённый непосредственно из ответа POST ID и GET-проверки до/после изменения title. Никаких других ресурсов и production не меняли.
