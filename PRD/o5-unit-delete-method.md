# O5: опциональный DELETE Unit — 2026-10-26

## Контракт и границы

Добавить `Methods\Unit::delete(Headers $headers, int $id): ResponseInterface`: передать `DELETE` по `uri('Unit', $id)->asString()` и исходные auth headers клиенту Guzzle, вернуть исходный ответ. Тела запроса и клиентской проверки ID нет; исключения и настройка `http_errors` остаются поведением Guzzle. Права, связанные записи и результат удаления определяет сервер; вызывающий код сам проверяет `success` в теле ответа. По исходнику generic-контроллер отвечает 404 для отсутствующего ID; на wire это не проверялось. Исход для Unit со ссылками не проверен.

Основание: закреплённый OpenAPI содержит `DELETE /rest/api/Unit/{ID}`; `UnitController` наследует generic `doRestDelete()`, который загружает запись по ID и вызывает `delete()`. Это чтение checkout `vetmanager-extjs` на `5c28b627077b4d59c75dc2204a3df8e0d722f291` (`rest/protected/controllers/UnitController.php`, `rest/protected/extensions/restfullyii/components/ERestController.php`); его тождество развернутому devtr6 не доказано. В devtr6 дважды удалялись только созданные технические Unit: ID 48 и 50, DELETE вернул 200 и `success=true`; последующие GET и агрегаты Redash подтвердили отсутствие. Для ID 48: после DELETE GET вернул пустую коллекцию, Redash в 11:34 MSK подтвердил ноль по ID и точному маркеру. Для ID 50: GET по ID и поиск маркера дали отсутствие, Redash в 08:59:15 UTC подтвердил ноль по ID и префиксу маркера. Дополнительная хронология — `PRD/o5-schema-evidence-2026-10-26.md`. Новых write-проб этот этап не требует.

Это расширение `http_method_support`, а не схемы: `schema_support` остаётся `none`. Предыдущее описание 17-символьного `Unit.title` ошибочно: сохранённый маркер длиной 16, wire-исход для 17 неизвестен.

## Приёмка

- Unit-тест проверяет DELETE, точный URI/ID, auth header, отсутствие тела и исходный ответ; моки 404 проверяют `ClientException` при `http_errors=true` и исходный ответ при `false`.
- В матрице только `delete_rest_api_Unit_ID.http_method_support` меняется с `none` на `unit_delete`; `schema_support=none`, остальные операции не меняются. Контрактный скрипт сверяет наличие DELETE в исходнике.
- README, Roadmap и Tasks описывают узкий метод и границы; прежние POST/PUT не меняются.
- Предыдущие документы O5 больше не утверждают успешную пробу 17 символов: маркер был длиной 16, исход для 17 неизвестен.
- `python3 -I scripts/check_openapi_contract.py`, `make all PHP_VERSION=8.3`, существующий read-only набор `make integration` на devtr6 с числом тестов и пропусков, CI точного SHA, включая PHP 7.3; независимое ревью PRD до реализации и diff после неё. Интеграция не перепроверяет DELETE живьём.

## Ревью и проверки

Claude Sonnet до реализации вернул замечания: уточнить, что интеграция read-only и не доказывает новый метод живьём; сослаться на сохранённые wire-доказательства; зафиксировать 404 и оба режима Guzzle; явно описать границу прав/связей и единственное изменение матрицы. Замечания приняты и внесены выше. Новые live write-пробы не нужны, поскольку две прежние подтверждены cleanup.

Claude Sonnet после реализации указал, что контрактный скрипт мог принять одно слово `DELETE` в комментарии, поскольку URI уже встречался в `put()`. Исправлено: проверяется сигнатура и вызов Guzzle внутри `delete()`. Также уточнены источник 404 (checkout ExtJS, не wire), SHA серверного исходника, проверка отсутствия `Content-Type` и доказательства очистки ID 48. Остальные замечания касались фиксации результатов проверок и CI; они заполняются ниже по факту. Замечание о дополнительном live DELETE отклонено: два контролируемых удаления уже доказаны, новый запрос создал бы запись только ради повтора.
