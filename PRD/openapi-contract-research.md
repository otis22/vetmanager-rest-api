# Исследование оставшихся контрактов OpenAPI

Источник — локальный фиксированный JSON-снимок OpenAPI 1.3.1. Это исследовательская очередь после совместимого расширения, а не подтверждение серверной реализации.

## O4 — HTTP-операции

Снимок перечисляет 137 операций: 87 GET, 23 POST, 16 PUT и 11 DELETE. Нынешняя библиотека строит URI/заголовки/запросные параметры, но не исполняет HTTP-запросы. Решение: до появления подтверждённого набора method/path/query/body/status не добавлять клиентские обёртки. Для первого набора отдельно выбрать read-only GET, проверить на devtr6 тип ответа и статус, затем описать контракт запроса. Действующие URI-помощники методов не ограничивают.

## O5 — схемы и тела

В `components.schemas` 36 объектных схем, ни одна не содержит список `required`; 150 свойств помечены `nullable`. `requestBody` есть у 39 операций: 23 POST и 16 PUT; только у одной операции весь `requestBody` отмечен `required`. Эти метаданные нельзя трактовать как исчерпывающие правила сервера. Для каждой схемы и операции следующего этапа нужно сопоставить тестовый ответ или метаданные devtr6, типы и обязательность, затем исправить upstream `vetmanager-openapi` и синхронно обновить YAML/JSON по закреплённому SHA и хэшам. Пользовательские записи в артефакты не переносить.

## O6 — опциональная валидация

Матрица проверки: модель/поле/тип/nullable/фильтр/пагинация/request body. Для каждого правила нужны допустимые и отвергаемые значения на devtr6 и unit-контракт. Валидатор должен быть отдельным opt-in API. `Builder::where()`, `Builder::paginate()` и существующая сериализация остаются прежними. Ни одна схема из снимка пока не обосновывает глобальный запрет ранее допустимого значения.

## O7 — авторизация и ошибки

В снимке есть только схема `X-REST-API-KEY` и ответы 200/201. Библиотека также предоставляет token и service API key; их не удалять. На тестовом devtr6 отдельным безопасным набором запросов проверить статус, Content-Type, форму тела и заголовки для 400/401/403/404/409/422/429 и наблюдаемых 5xx, не провоцируя 5xx намеренно. Уточнить три способа авторизации. Проверенные схемы ошибок добавить сначала в upstream; обработчик ошибок проектировать после этого, не меняя действующие заголовки и исключения.

## O8b — полная карта поддержки

Текущий CI проверяет целостность снимка и матрицу URI-способностей по операциям. Таблицу поддержки схем и методного слоя добавить после O4–O7. `http_method_support: none` и `schema_support: none` в текущей матрице выражают фактическую границу библиотеки, а не отсутствие серверной операции.

## Отдельное исследование несовместимых вариантов

Для будущего major отдельно исследовать: удаление 13 прежних имён, замену регистра старых имён, изменение `uri()` и `Model::asString()`, автоматическую строгую валидацию существующего `Builder`, изменение формата `asKeyValue()` и отказ от token/service API key. Каждый вариант меняет прежний контракт; нужны инвентаризация потребителей, миграционный API, оценка влияния и решение владельца. В текущий минорный PR эти изменения не входят.
